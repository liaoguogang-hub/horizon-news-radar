## [SourceHut Account Takeover via XSS in Build Logs](https://blog.arusekk.pl/posts/srht-account-takeover/) ⭐️ 8.0/10

A security researcher discovered an account takeover vulnerability in SourceHut caused by a cross-site scripting \(XSS\) flaw in the ansi2html.py library used to render CI build logs. Crafted lines in a build log were transformed into HTML by ansi2html, allowing malicious scripts to execute in the browsers of users viewing that log. This vulnerability is significant because it affects SourceHut, a widely-used open-source CI/CD and code hosting platform, meaning any developer using its CI service to build untrusted or public projects could be exposed. An XSS-based account takeover on such a platform can lead to source code theft, supply chain attacks, and unauthorized repository access, with broad implications for the open-source ecosystem. The flaw originates in ansi2html.py version 1.9.4, which is also notable as the project that inspired the famous XKCD &\#x27;Bobby Tables&\#x27; comic. The XSS vulnerability stems from how ansi2html processes ANSI escape sequences in build logs without properly sanitizing the resulting HTML output before rendering it in users&\#x27; browsers.

rss · Lobsters \(技术社区\) · Sep 24, 20:38

**Background**: SourceHut \(sr.ht\) is an open-source collaborative software development platform offering Git/Mercurial hosting, CI/CD, issue tracking, and mailing lists, often favored by developers seeking lightweight, open alternatives to GitHub or GitLab. Cross-site scripting \(XSS\) is a class of web vulnerability where attackers inject malicious client-side scripts into pages viewed by other users, potentially allowing session hijacking and account takeover. ansi2html.py is a Python library that converts ANSI-colored terminal output \(such as build logs containing escape codes\) into HTML for browser display, and it has been a known XSS risk in CI systems for years.

The phase 3 ROAM/EORTC-1308 randomised controlled trial published in The Lancet found that adjuvant fractionated radiotherapy significantly improves disease-free survival in patients with WHO grade 2 atypical meningioma after complete surgical resection. The authors recommend that adjuvant radiotherapy should be considered in these patients when the prevention of recurrence is prioritized over potential delayed adverse effects. This is the first multicentre randomised controlled trial to provide class I evidence on adjuvant radiotherapy for atypical meningioma, and its findings could reshape standard post-surgical treatment protocols for this patient population. Atypical meningiomas account for 15–20% of all meningiomas and carry a high recurrence risk, making this evidence directly relevant to thousands of patients worldwide. The trial was an international, multicentre, open-label, phase 3 randomised controlled study. The decision to use radiotherapy must weigh recurrence prevention against potential delayed adverse effects, and treatment choices should be individualized through discussion with each patient.

rss · The Lancet · 最新文章 · Sep 25, 10:08

**Background**: Meningiomas are tumours arising from the meninges, the membranes surrounding the brain and spinal cord. The WHO classifies them into grades 1 through 3, with grade 2 \(atypical\) meningiomas being intermediate-grade tumours that account for roughly 15–20% of cases and are characterised by features such as 4–19 mitotic figures per 10 high-power fields. Because atypical meningiomas have a substantially higher recurrence rate than grade 1 \(benign\) meningiomas, there has been longstanding debate about whether adjuvant radiotherapy immediately after surgery can reduce recurrence risk. ROAM/EORTC-1308, sponsored by the European Organisation for Research and Treatment of Cancer \(EORTC\), was specifically designed to address this question with rigorous randomised methodology.

## [Go Experiments with Platform-Independent SIMD in Standard Library](https://go.dev/blog/simd-experiment) ⭐️ 7.0/10

Go has introduced an experimental, platform-independent SIMD package in its standard library under GOEXPERIMENT=simd, planned for Go 1.26 and 1.27. The new package achieves roughly 5x speedup over scalar code with about 11% overhead compared to architecture-specific SIMD, and uniquely supports variable-length vectors such as ARM SVE and RISC-V RVV. This addition fills a long-standing gap in Go&\#x27;s ecosystem by giving developers a portable way to write SIMD-accelerated code without relying on compiler auto-vectorization or CGO-based native libraries. It levels the playing field with languages like C++ \(std::simd\) and Rust \(portable SIMD crates\) and could significantly benefit performance-critical domains such as image processing, ML inference, and database operations written in pure Go. On platforms lacking SIMD instructions or archsimd support, all operations are emulated so the code still runs. Current support covers amd64 in the portable simd package, with archsimd additionally gaining Wasm and ARM64 support in Go 1.27 RC1. The size-agnostic design unifies handling of fixed-width \(SSE/AVX/NEON\) and variable-length \(SVE/RVV\) vector hardware under a single API.

hackernews · Hacker News \(热门\) · Sep 25, 11:47 · [Discussion](https://news.ycombinator.com/item?id=49843269)

**Background**: SIMD \(Single Instruction, Multiple Data\) instructions let a CPU perform the same operation on multiple data values in parallel, dramatically speeding up tasks like numerical computation, image processing, and cryptography. Traditionally, SIMD programming has required architecture-specific intrinsics \(e.g., SSE for x86, NEON for ARM\), which makes code hard to port across platforms. Recent efforts such as C++ std::simd, Rust&\#x27;s portable SIMD crates, and Google&\#x27;s Fearless SIMD aim to abstract these differences. Go previously had no first-class SIMD story, forcing performance-critical projects to either rely on compiler auto-vectorization or drop down to C/C++ via cgo, breaking Go&\#x27;s pure-deployment model.

## [Breaking Out of Avast Antivirus Sandbox via CVE-2025-13032](https://www.safateam.com/intelligence-hub/research/technical-articles/cve-2025-13032-entering-and-breaking-the-avast-antivirus-sandbox-part-2) ⭐️ 7.0/10

Security researcher SafaTeam published Part 2 of a technical analysis detailing CVE-2025-13032, a double-fetch \(TOCTOU race condition\) vulnerability in Avast Antivirus&\#x27;s kernel driver \($aswSnx$\) that enables a full local privilege escalation on an up-to-date Windows 11 system. Part 1 \(published earlier\) revealed four kernel heap overflows in the same driver, while Part 2 demonstrates the complete exploit chain for sandbox escape and privilege escalation. This vulnerability affects a widely deployed consumer and enterprise antivirus product, demonstrating that security tools themselves can become attack vectors for full system compromise. The exploit chain bypasses Avast&\#x27;s custom sandbox designed to isolate suspicious code, undermining a core defensive layer that millions of users rely on for protection. The vulnerability is classified as a double-fetch bug, a variant of TOCTOU where a kernel driver reads the same memory location twice and an attacker can modify the value between the two reads. Part 2 of the research provides a working privilege escalation exploit; the sandbox manipulation technique detailed in Part 1 was required to reach the vulnerable attack surface in the $aswSnx$ driver. The flaw was disclosed responsibly and patched by Avast.

hackernews · Hacker News \(热门\) · Sep 25, 07:03 · [Discussion](https://news.ycombinator.com/item?id=49841115)

**Background**: A TOCTOU \(Time-of-Check to Time-of-Use\) race condition occurs when a program validates a resource&\#x27;s state and then acts on it moments later, assuming nothing changed in between—an attacker who can modify the resource during that window wins. Antivirus products like Avast run suspicious files inside sandboxes \(isolated environments\) to observe behavior without risking the host system; escaping the sandbox is a high-value target for attackers because it means malicious code can execute on the real machine. Sandbox evasion has a long history, with malware authors using techniques like timing checks \(e.g., GetTickCount\) to detect accelerated or virtualized environments and polymorphism to bypass static signature scanning.
