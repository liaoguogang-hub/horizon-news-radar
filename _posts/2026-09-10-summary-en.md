## [DeepSeek Releases V4.1 Flash with Ultra-Low $0.003 Cache Pricing](https://twitter.com/deepseek_ai/status/2097930608790167907) ⭐️ 9.0/10

DeepSeek released V4.1 Flash, a 552B-parameter model featuring a new Causal Encoder-Decoder \(CED\) architecture with only 8B active parameters for input and 16B for output, along with a detailed technical report on Hugging Face. The release includes groundbreaking cache hit pricing at $0.003 per million tokens, dramatically undercutting typical cache pricing in the industry. This release could reshape LLM API economics by making cached input tokens cheaper than the network bandwidth required to transmit them, potentially pushing developers toward context-caching architectures over traditional chat completion APIs. DeepSeek&\#x27;s continued pattern of pairing frontier-scale training with openly published technical details also intensifies pressure on closed labs like OpenAI and Anthropic to match both pricing and transparency. V4.1 Flash natively processes images and uses a 40-layer Transformer organized as a 20-layer causal encoder plus a 20-layer decoder. Compared to the prior V4 Flash \(284B parameters\), V4.1 Flash roughly doubles parameter count to 552B, which likely explains its benchmark gains but reduces its practicality for local deployment. The $0.003/M cached-token rate is roughly an order of magnitude below competitors like OpenAI&\#x27;s GPT-5.5 at $0.50/M cached input.

hackernews · Hacker News \(热门\) · Sep 10, 06:11 · [Discussion](https://news.ycombinator.com/item?id=49639090)

**Background**: LLM APIs typically charge separately for input tokens, output tokens, and cached input tokens, where cached tokens reuse previously computed key-value \(KV\) cache state instead of re-processing the full prompt. Cache hit pricing is significant because long-running agentic or coding workflows often re-send large prompt prefixes \(system prompts, codebase context\) on every turn, making caching one of the largest cost-optimization levers available. DeepSeek&\#x27;s V3 and V4 lines have emphasized hybrid attention mechanisms—combining Compressed Sparse Attention \(CSA\) and Heavily Compressed Attention \(HCA\)—to cut long-context KV cache and inference FLOPs, enabling both efficient serving and aggressive pricing.

## [Critical RCE Vulnerability Found in Forgejo ≤16.0.3](https://codeberg.org/forgejo/forgejo/src/branch/forgejo/release-notes-published/16.0.4.md) ⭐️ 8.0/10

A critical remote code execution \(RCE\) vulnerability has been discovered in Forgejo versions ≤16.0.3, exploitable through malicious template repositories during repository initialization. The vulnerability has been patched in Forgejo 16.0.4. Forgejo is a widely-used self-hosted Git platform powering services like Codeberg, so this vulnerability poses significant risk to any instance running the affected versions, potentially allowing attackers to read arbitrary data and execute arbitrary processes on the host. Self-hosted Git platforms are core infrastructure for many organizations, making timely patching critical. The vulnerability \(tracked as CVE-2025-68937\) involves directory traversal in the template repository processing logic, where variable template expansion interferes with git repository initialization, allowing remote authenticated attackers to process arbitrary files and achieve RCE. The fix in PR \#14301 ensures template expansion cannot interfere with git repo initialization, and Gitea has confirmed it is already protected against this issue.

hackernews · Hacker News \(热门\) · Sep 10, 15:57 · [Discussion](https://news.ycombinator.com/item?id=49645907)

**Background**: Forgejo is a lightweight, self-hosted Git service forked from Gitea, maintained by a community under the Codeberg e.V. nonprofit organization. A template repository in Forgejo is a pre-configured repository that can be used as a starting point for new repositories, with variable substitution applied to files listed in .forgejo/template during initialization. Remote Code Execution \(RCE\) vulnerabilities are among the most severe security flaws because they allow attackers to run arbitrary code on the server, potentially compromising the entire system.

## [CHERIoT: Capability-Based Isolation for MMU-less Embedded Devices](https://queue.acm.org/doi/10.1145/3831361) ⭐️ 8.0/10

ACM Queue has published an in-depth article explaining how CHERIoT uses capability-based hardware isolation to deliver strong memory safety and compartmentalization on resource-constrained embedded devices that lack a Memory Management Unit \(MMU\). The article details how Microsoft&\#x27;s CHERIoT-Ibex implementation extends the open-source Ibex RISC-V core with CHERI capabilities to enforce memory isolation at the hardware level. This matters because embedded and IoT devices are increasingly targeted by attackers but typically lack the MMU-based protections that desktops and servers rely on for process isolation. CHERIoT offers a practical path to bring hardware-enforced memory safety to billions of low-cost microcontrollers, potentially reducing entire classes of memory-corruption vulnerabilities in the IoT ecosystem. CHERIoT is a 32-bit RISC-V extension optimized for IoT, derived from the broader CHERI project \(a collaboration between SRI International and the University of Cambridge\). It uses hardware-enforced CHERI capabilities—fat pointers containing an address plus bounds and permissions metadata—rather than MMU page tables, and studies show its area overhead on Ibex is minimal. Compartmentalization relies on a small Trusted Computing Base to mediate controlled sharing between compartments.

rss · Lobsters \(技术社区\) · Sep 10, 14:59

**Background**: CHERI \(Capability Hardware Enhanced RISC Instructions\) is a long-running research project that revisits fundamental hardware and software design choices to improve system security through capability-based addressing, where each pointer carries unforgeable metadata about what memory it may access. CHERIoT, started in 2019, is Microsoft&\#x27;s effort to scale CHERI down to very small embedded systems such as microcontrollers used in IoT. Traditional memory safety on such devices is difficult because most low-end MCUs lack an MMU, making per-process address space isolation impossible; developers typically rely on bare-metal trust boundaries that are easily compromised by a single memory bug.

## [Git Never Deletes: Snapshots Keep Deleted Data Alive](https://dev.to/machineunderneath/git-never-deletes-anything-what-a-commit-actually-stores-3nil) ⭐️ 6.0/10

An article demonstrates that Git commits store complete snapshots rather than diffs, meaning files deleted in later commits remain fully recoverable using just two commands: \`git log --all --diff-filter=D --name-only\` to find them and \`git cat-file -p &lt;commit&gt;:&lt;path&gt;\` to read them back. This has direct security implications: sensitive data such as API keys committed and then removed remain readable in the repository history, accessible to anyone with repository access including those who clone a fresh copy. Developers must understand this to avoid leaking secrets, and teams should adopt remediation strategies like rewriting history or using secret-scanning tools. Running \`git gc\` does not remove deleted-file objects because the original commit is still reachable, and gc only collects unreachable objects. Git&\#x27;s content-addressable storage means identical file contents across a hundred files produce just one blob object, and packing reduces 51 versions of a 200,000-line file from 22,032 KiB loose to 847.96 KiB packed \(a 26× reduction\) by storing two full versions and 49 as deltas of ~94 bytes each.

rss · Dev.to · Sep 10, 20:44

**Background**: Git uses a content-addressable storage model, meaning every object \(blob, tree, commit, or tag\) is identified by a SHA-1 hash of its own contents. When you make a commit, Git stores a full snapshot of the entire project as a tree object referencing blob objects for each file, rather than recording only the changes \(a diff\). This design enables automatic deduplication—identical content always produces the same hash—while tools like \`git gc\` and packfiles later compress history by storing deltas. The trade-off is that nothing is truly deleted until all references to an object are gone, which is why sensitive information persists unless history is actively rewritten with tools like \`git filter-repo\`.
