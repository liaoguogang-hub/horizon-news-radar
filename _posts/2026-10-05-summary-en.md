## [Dust: First Zeroth-Order Pretraining Competitive with Backpropagation](https://qlabs.sh/research/dust) ⭐️ 8.0/10

Researchers at Q Labs have introduced Dust, a zeroth-order optimization method that pretrains transformer language models without backpropagation by perturbing activations independently at every token, making each token a virtual population member evaluated in parallel within a single forward pass. This is the first backpropagation-free method shown to be competitive with backprop at pretraining scale, which could fundamentally reshape deep learning by removing the need to store activations and gradients, dramatically lowering memory requirements and enabling more efficient distributed training of large models. The method uses node perturbation on activations rather than weight perturbation, and leverages token-level parallelism so that one forward pass effectively evaluates a population of perturbed models simultaneously, avoiding the scalability issues that have plagued prior zeroth-order approaches.

rss · Hacker News \(热门\) · Oct 5, 21:15

**Background**: Backpropagation has been the dominant algorithm for training neural networks since the deep learning revolution, but it requires storing all intermediate activations for the backward pass, making it memory-intensive. Zeroth-order methods estimate gradients by perturbing inputs and observing output changes, avoiding the need for backprop entirely. Prior attempts such as Feedback Alignment, Forward-Forward \(FF\), and NoProp have explored biologically plausible or memory-efficient alternatives, but none had matched backprop at the scale of pretraining transformer language models.

## [Async Rust: Where Does the Scheduler Live?](https://herecomesthemoon.net/2026/10/async-rust-where-does-the-scheduler-live/) ⭐️ 7.0/10

A detailed blog post explores the architectural question of where the scheduler resides in async Rust runtimes, examining how futures are managed and executed within the runtime model. Understanding scheduler placement is fundamental for Rust developers writing async code, as it clarifies performance characteristics, runtime choice trade-offs, and the division of responsibilities between the standard library and external runtime crates like Tokio. In Rust&\#x27;s async model, the compiler transforms async functions into state machines \(futures\), but the actual execution—polling these futures, managing task queues, and reacting to I/O events—is delegated to external runtime libraries that bundle a reactor with one or more executors.

rss · Lobsters \(技术社区\) · Oct 5, 18:31

**Background**: Rust&\#x27;s async/await syntax was stabilized in 2019, but unlike languages such as Go or JavaScript, Rust intentionally did not bundle a built-in runtime. Instead, async functions compile to anonymous future types that implement the Future trait, and the standard library provides only the core trait definitions. This means every Rust async program must depend on an external runtime crate—Tokio being the most prominent—to actually run the futures, schedule tasks, and handle I/O events. Tokio has grown beyond a simple runtime into a comprehensive framework that includes modules for filesystem, networking, process, and signal handling.

## [Mold 3.0.0 Released: Major Update to High-Performance Linker](https://github.com/rui314/mold/releases/tag/v3.0.0) ⭐️ 7.0/10

Mold 3.0.0, a major version release of the high-performance, open-source linker developed primarily by Rui Ueyama and written in C++, has been published on GitHub. As a drop-in replacement for traditional Unix linkers, this major version bump typically signals significant new features, architectural changes, or improvements over the 2.x series. Mold is widely recognized as one of the fastest open-source linkers available, often running several times faster than GNU ld and LLVM lld, which directly translates into reduced build times for large C, C++, and Rust projects. For developers working on massive codebases like Chromium, where linking can take many seconds, using mold can dramatically shorten debug-edit-rebuild cycles and boost overall productivity. Mold achieves its speed through extensive parallelization across nearly all stages of linking, the implementation of more efficient algorithms, and the use of techniques like running two processes simultaneously. It supports a wide range of architectures including x86-64, ARM64, RISC-V, LoongArch, and PowerPC, while macOS support requires the separate commercial &\#x27;sold&\#x27; linker. Users can invoke it via \`-fuse-ld=mold\` for Clang or GCC 12.1.0+, or through \`.cargo/config.toml\` for Rust projects.

rss · Lobsters \(技术社区\) · Oct 5, 14:24

**Background**: A linker is a build tool that combines multiple object files \(produced by a compiler\) and library files into a single executable or shared library. It performs crucial tasks like symbol resolution and address relocation, ensuring that references between different code modules are correctly connected. The linking step can become a significant bottleneck in large projects, which is why fast linkers like mold are highly valued in systems programming and large-scale C/C++ development. Mold was originally created by Rui Ueyama, who also authored LLVM&\#x27;s lld linker, with mold being written from scratch in C++ to maximize parallelism.

## [Dostoevsky: Adaptive LSM-Tree Merging for Better Space-Time Trade-Offs](https://nivdayan.github.io/dostoevsky.pdf) ⭐️ 7.0/10

The paper introduces Dostoevsky, an adaptive key-value store built on the Fluid LSM-tree framework that eliminates superfluous merging by navigating the design space based on application workload and hardware. It uses Lazy Leveling to skip merges at all LSM-tree levels except the largest, reducing update I/O while preserving lookup and storage bounds. LSM-tree based engines like RocksDB, LevelDB, and Cassandra power countless production databases, and compaction/merging is their most expensive operation. Dostoevsky&\#x27;s workload-aware adaptive merging delivers empirically better space-time trade-offs, directly translating to lower write amplification, faster writes, and reduced storage costs in real-world deployments. Dostoevsky generalizes Lazy Leveling within the Fluid LSM-tree framework to enable adaptive, workload- and hardware-aware merging policies. It is implemented on top of RocksDB and empirically dominates state-of-the-art approaches in both performance and space efficiency. The paper was authored by Niv Dayan and published at SIGMOD 2018.

rss · Lobsters \(技术社区\) · Oct 5, 20:18

**Background**: LSM-trees \(Log-Structured Merge-trees\) are write-optimized data structures that buffer writes in memory and periodically flush sorted runs \(SSTables\) to disk, merging them in levels to keep reads efficient. The background merging/compaction process is essential for read performance and space reclamation but causes significant write amplification and I/O overhead. Production systems like RocksDB, LevelDB, and Cassandra all rely on LSM-trees and must carefully tune compaction strategies to balance read cost, write amplification, and space amplification—the space-time trade-off.
