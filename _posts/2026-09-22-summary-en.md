## [Cloudflare Python Workers Reach General Availability](https://simonwillison.net/2026/Sep/21/cloudflare-python-worker/) ⭐️ 8.0/10

Cloudflare has promoted Python support in its Workers serverless platform from a two-year preview to general availability, making Python a fully supported first-class language on the Cloudflare Developer Platform. The implementation runs Python code compiled to WebAssembly via Pyodide inside Cloudflare&\#x27;s V8-based workerd runtime. This is a major milestone for Python developers who want to deploy code on edge infrastructure, lowering the barrier for serverless Python adoption at global scale. It also reflects Cloudflare&\#x27;s deepening investment in the Python ecosystem, given that two of the credited contributors are Pyodide core maintainers. Because execution relies on Pyodide within WebAssembly, both Python&\#x27;s multiprocessing and threading modules are non-functional in the runtime. Local development is handled by the pywrangler CLI \(distributed on PyPI as workers-py\), which embeds a 123MB workerd binary to simulate the full Cloudflare stack locally, including Pyodide-on-WASM execution inside V8.

rss · Simon Willison \(AI 跨行业洞察\) · Sep 21, 22:25

**Background**: Pyodide is a port of CPython compiled to WebAssembly via Emscripten, allowing Python code to run in browser-like environments and supporting many pure Python packages from PyPI as well as select C/C++/Rust extensions. workerd is Cloudflare&\#x27;s open-source JavaScript and WebAssembly server runtime, based on the same code that powers Cloudflare Workers and built on the V8 engine used by Chromium and Node.js. Workers themselves are Cloudflare&\#x27;s serverless edge compute platform, historically limited to JavaScript before expanding to other languages such as Python and, more recently, WebAssembly-native workloads.

## [Drop: A Rootless Linux Sandbox with gVisor Support](https://droprun.sh/) ⭐️ 7.0/10

Drop is a newly relaunched rootless Linux sandbox that uses Linux namespaces \(user, mount, network, PID, IPC, cgroup\) to isolate third-party programs locally, with optional integration of gVisor as a user-space kernel for added protection. The developer describes the workflow as inspired by Python&\#x27;s virtualenv but with enforced isolation rather than convention-based isolation, and each sandbox gets its own disposable writable home directory with selected host configs mounted mostly read-only. Running untrusted code locally—such as AI coding agents or dependencies from third-party packages—remains a significant security risk, and containers/VMs often impose too much productivity overhead for everyday developer workflows. Drop targets the growing need for lightweight, ergonomic isolation specifically for local development and agent execution, where many teams \(including frontier AI labs\) are reportedly building or seeking comparable infrastructure. The sandbox requires no root privileges and works by isolating environments using standard Linux namespaces; gVisor integration is optional and adds a user-space kernel layer in Go that intercepts syscalls, defending against host kernel exploits. Differentiators claimed over nsjail/runc are not deeply documented, and the developer acknowledges rebuilding some of the same primitives—prompting community questions about what truly sets Drop apart in an already crowded sandboxing landscape.

hackernews · Hacker News \(热门\) · Sep 22, 13:52 · [Discussion](https://news.ycombinator.com/item?id=49801329)

**Background**: Linux sandboxes isolate processes by restricting what they can see and do on the host using mechanisms such as namespaces, cgroups, seccomp, and capabilities; &\#x27;rootless&\#x27; variants avoid requiring elevated privileges, improving safety. gVisor is an open-source application kernel written in Go that sits between a sandboxed workload and the host Linux kernel, intercepting system calls in userspace to reduce the attack surface exposed to untrusted code. Other comparable tools include nsjail, runc \(the OCI reference runtime behind Docker/Kubernetes\), bubblewrap, and Landlock-based solutions.

## [AMD RDRAND Bug: Zen 2/3 CPUs Cannot Generate Zero Values](https://board.flatassembler.net/topic.php?t=24261) ⭐️ 7.0/10

A bug has been discovered in AMD&\#x27;s RDRAND instruction on Zen 2 and Zen 3 processors where the hardware random number generator never returns a value of zero \(all bits set to 0\), particularly affecting 16-bit RDRAND outputs. AMD has issued an official security bulletin acknowledging the issue and is expected to release a microcode update to address it. RDRAND is widely used in cryptographic applications, TLS handshakes, OS entropy pools, and scientific simulations as a source of hardware randomness. A biased random number generator that omits entire output values can subtly undermine the statistical quality of downstream random streams, potentially weakening cryptographic protocols and security guarantees that assume uniform distribution. The bug was first noticed in 16-bit RDRAND calls, where the output is never exactly zero; 32-bit RDRAND appears less affected but may also exhibit similar bias at lower bit widths. Community testing across multiple Zen 2 and Zen 3 SKUs \(including Ryzen 5 3600\) has reproduced the issue, though not all chips are equally affected, suggesting the root cause may lie in the entropy conditioning circuit.

hackernews · Hacker News \(热门\) · Sep 22, 08:39 · [Discussion](https://news.ycombinator.com/item?id=49798204)

**Background**: RDRAND is an x86 instruction introduced by Intel \(codenamed Bull Mountain\) and later adopted by AMD, designed to return hardware-generated random numbers compliant with standards like NIST SP800-90 and FIPS 140-2. The instruction draws entropy from on-chip physical sources \(such as thermal noise\) and conditions it through cryptographic mechanisms before exposing the output to software. AMD&\#x27;s Zen 2 and Zen 3 microarchitectures power a wide range of consumer Ryzen processors as well as EPYC server chips and Threadripper workstation CPUs, making any RDRAND bug potentially impactful across both desktop and data center environments.

Security-oriented developers pointed out that hardware RNG outputs are rarely used directly and instead seed CSPRNGs, limiting practical impact, and recommended using extendable-output functions \(XOFs\) that combine entropy from multiple sources for security-critical applications.
