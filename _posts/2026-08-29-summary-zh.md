## [htmx 4.0 正式发布，集成 Fetch API 与 Idiomorph](https://four.htmx.org/announcements/2026-08-28-htmx-4.0.0-is-released) ⭐️ 8.0/10

htmx 4.0 正式发布，这是该库自 2.x 以来的首次重大版本升级。新版本将底层 XMLHttpRequest 替换为现代 Fetch API，并集成了 idiomorph DOM 变形算法，实现无缝的 HTML 替换。 htmx 代表了一股日益壮大的反 SPA 主流架构的潮流，倡导服务器直接返回 HTML 的超媒体驱动应用。本次重大版本发布标志着该方法正在趋于成熟，成为一种可行的长期替代方案，尤其适合追求更精简技术栈、更少 JavaScript 负担的开发者。 htmx 的核心属性（hx-get、hx-post、hx-target、hx-boost、hx-swap、hx-trigger 等）保持不变，大多数 2.x 应用只需少量配置调整即可兼容。但自动属性继承机制被移除，需改用显式的 :inherited 修饰符；由于 Fetch API 的事件模型不同，开发者必须更新事件监听器。同时新增了原生流式响应支持作为升级点。

hackernews · Hacker News \(热门\) · 8月28日 13:28 · [社区讨论](https://news.ycombinator.com/item?id=49478178)

**背景**: htmx 是一个轻量级 JavaScript 库，允许开发者直接通过 HTML 属性使用 AJAX、CSS 过渡和 WebSockets，无需编写 JavaScript 即可实现交互。它是 intercooler.js 的继任者，遵循 REST 架构中的 HATEOAS 约束——由服务器通过超媒体链接和表单控制 UI 流程，而非客户端通过 JSON API 管理状态。这种超媒体驱动方式与 React 等框架推广的单页应用（SPA）模式形成对比，后者主要依赖客户端从 JSON 数据渲染 UI 并在浏览器中维护复杂状态。

## [Cloudflare 通过 DNS 缓存优化节省 100TB 内存](https://blog.cloudflare.com/dns-cache-memory-optimization-1111/) ⭐️ 8.0/10

Cloudflare 发布了一篇详细的工程博客，介绍了他们如何通过五项 Rust 级别的内存优化，对内部系统「Big Pineapple」（为 1.1.1.1 公共 DNS 解析器提供支持）的 DNS 缓存布局进行优化，将单条记录的内存占用减少了 56%，在其全球服务器集群中释放了约 100 TB 内存。 这一成果意义重大，因为 1.1.1.1 是全球最大的公共 DNS 解析器之一，服务着数亿用户；节省 100 TB 内存直接转化为更低的基础设施成本、更高的缓存命中率和更快的查询响应速度——这些经验对于任何运行大规模内存缓存系统的团队都具有直接参考价值。 这些优化是在 Cloudflare 自研 DNS 服务器 Big Pineapple 的 Rust 数据结构层面完成的。通过重新设计单条 DNS 缓存记录在内存中的布局（而非改变缓存淘汰策略或 TTL 行为），他们将每条记录的内存占用减少了 56%，这一收益在数十亿条缓存记录上得到了显著累积。

rss · Lobsters \(技术社区\) · 8月28日 06:54

**背景**: DNS（域名系统）解析器负责将 example.com 这类人类可读的域名转换为计算机用于建立连接所需的 IP 地址。为了降低延迟并减少向上游查询的次数，解析器会维护近期 DNS 响应的缓存。Cloudflare 的 1.1.1.1 是一个注重隐私的免费公共 DNS 解析服务，与 Google Public DNS（8.8.8.8）等同类服务竞争，经过独立测量被认定为最快的公共解析器之一。由于其服务全球海量用户，其内存缓存的规模与效率对性能与运营成本都有着举足轻重的影响。

## [Anthropic 推出 Model Hardware Standard，赋能 AI Agent 控制物理设备](https://arstechnica.com/ai/2026/08/anthropics-new-hardware-standard-lets-ai-agents-control-the-physical-world/) ⭐️ 8.0/10

## [GCC 在非可执行栈上间接调用嵌套函数](https://uecker.codeberg.page/2026-08-29.html) ⭐️ 6.0/10

GCC 贡献者 Martin Uecker 发表了一篇博文，分析了一种无需可执行栈即可在 GCC 中对嵌套函数进行间接调用的技术，通过从生成的蹦床中提取代码地址和静态链，并使用 \_\_builtin\_call\_with\_static\_chain 来绕过它。这使得旧版 GCC 能够在禁用可执行栈的安全加固环境中支持嵌套函数。 这之所以重要，是因为可执行栈的要求代表了一个显著的安全弱点，能够在不使用可执行栈的情况下调用嵌套函数，可以在安全敏感的场景中更安全地使用这个 GNU C 扩展。它还影响到在强制要求不可执行内存保护的加固 Linux 发行版和嵌入式系统上的可移植性。 该变通方法针对的是早于基于描述符的嵌套函数支持的旧版 GCC，编译后使用 patchelf 清除可执行栈标志。Uecker 的技巧特别在运行时同时恢复函数指针和静态链指针，这两者通常只在栈上分配的蹦床代码中嵌入在一起。

rss · Hacker News \(热门\) · 8月29日 14:20

**背景**: GCC 的嵌套函数扩展允许在一个函数内部定义另一个函数，内部函数通过一个隐藏的静态链指针捕获外层作用域中的变量。为了支持获取此类函数的地址，GCC 传统上会在栈上生成一小段可执行代码，称为蹦床（trampoline），它在跳转到实际函数之前设置好静态链。这个蹦床要求栈被标记为可执行，这与现代操作系统用来阻止从数据区域执行代码的 NX 位（No-Execute bit）安全特性相冲突。较新版本的 GCC 提供了基于描述符的嵌套函数实现来避免此需求，但旧版本默认仍依赖蹦床。
