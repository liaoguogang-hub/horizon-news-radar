## [Cisco ISE CVE-2026-76460：身份验证绕过严重漏洞已被主动利用](https://dev.to/bianliang/cisco-ise-authentication-bypass-cve-2026-76460-what-defenders-need-to-do-now-3ek7) ⭐️ 9.0/10

Cisco 于 2026 年 9 月 16 日披露了 CVE-2026-76460，这是 Cisco Identity Services Engine（ISE）和 ISE-PIC 中一个 CVSS 评分为 10.0 的身份验证绕过漏洞，攻击者无需认证即可通过向 API 端点发送特制请求获得 root 权限。Cisco PSIRT 已确认该漏洞正在被主动利用，影响 3.1 至 3.5 所有版本的 ISE 配置，且目前没有可用的临时缓解措施。 Cisco ISE 是业界领先的网络访问控制（NAC）平台，负责管控企业网络中用户和设备的接入权限，因此 ISE 设备一旦被获取 root 权限，攻击者就可以静默修改访问策略、横向移动至内部子网，并瓦解依赖 ISE 的零信任架构。鉴于漏洞已被确认在野外利用，且互联网上可观测到的 ISE 实例超过 4,000 个，企业防御者面临的运营压力极为紧迫。 该漏洞源于某个 API 端点对身份验证的强制执行不足，攻击者还可以删除日志条目以妨碍取证调查——需要关注的一个具体入侵指标是访问日志中名为 &\#x27;dummyuser&\#x27; 的账户活动。Cisco 已发布修复补丁，对应版本为 3.1 Patch 12、3.2 Patch 11、3.3 Patch 12、3.4 Patch 7 和 3.5 Patch 4；在没有临时缓解措施的情况下，防御者应使用基础设施 ACL 限制管理接口的访问，并立即优先完成补丁安装。

**背景**: Cisco Identity Services Engine（ISE）是一种下一代网络访问控制（NAC）和安全策略管理平台，可在有线、无线和 VPN 环境中统一并自动化基于角色的访问控制，是众多零信任架构的核心组件。CVSS（通用漏洞评分系统）是一个用于评估漏洞严重程度的开放标准，10.0 分代表 CVSS v3.1 中的最高严重程度，意味着该漏洞可被远程利用、无需身份验证或用户交互，并会对机密性、完整性和可用性造成严重影响。API 端点上的身份验证绕过意味着服务器在处理请求之前未能验证调用者身份，因此任何能够访问该端点的攻击者都可以直接调用特权操作。

## [Android 17 新增 Pixel 独占 API，不再同步至 AOSP](https://grapheneos.social/@GrapheneOS/117282080803799576) ⭐️ 8.0/10

Android 17 新增了仅限 Pixel 设备使用的 API，且未将其发布到 Android 开源项目（AOSP），这是自 Android 3.x 以来 Google 首次在 AOSP 之外添加新的平台 API。GrapheneOS 公开对此变化表示担忧，并指出部分 9 月的平台安全补丁对非 Pixel 厂商也存在延迟发布的情况。 这标志着 Android 历史上开放模式的重大转变，削弱了 GrapheneOS 等替代 Android 发行版跟进新平台功能的能力。此举表明 Google 正加强对 Android 演进方向的掌控，可能导致 Pixel 与非 Pixel 设备之间的生态碎片化，并引发人们对开源 Android 项目长期可持续性的担忧。 Google 仍然每年两次向公众发布完整的 AOSP 源代码更新，但现在会发布四次仅限 Pixel 的更新，包括 SDK 和文档。Google 还会每月向「受信」OEM 提供安全补丁回溯——GrapheneOS 多年来一直可参与此计划——但新的 Pixel 独占 API 对外部开发者不可用。

## [Cloudflare 用数学方法节省 100TB 内存](https://blog.cloudflare.com/saving-100-tb-of-ram-with-math/) ⭐️ 8.0/10

Cloudflare 工程师重写了基于 Pingora 的负载均衡服务，用基于统计学的数学方法替换了庞大的哈希环查找表（用 Rust 实现），在全球网络中回收了超过 100TB 内存，内存占用减少约 90%。 在 Cloudflare 的规模下，即使是微小的百分比优化也能转化为巨大的绝对资源节省，从而降低基础设施成本和能耗。这一方案表明，重新审视成熟算法中的基本假设，能够在大规模分布式系统中产生超预期的收益。 此次优化针对的是 pingora-ketama 组件，该组件原本为每台服务器存储大量虚拟哈希点以实现一致性哈希。通过概率分析，工程师们发现可以在保证负载均衡质量的前提下，大幅减少每台服务器的虚拟点数量。

hackernews · Hacker News \(热门\) · 9月18日 18:51 · [社区讨论](https://news.ycombinator.com/item?id=49758580)

**背景**: 一致性哈希是分布式系统中广泛使用的技术，用于在服务器池中分配请求，并在增删服务器时尽量减少扰动。其传统实现被称为「哈希环」（ketama 是其中一种流行变体），会为每台服务器分配多个虚拟点以保证均匀分布，但这需要在内存中存储庞大的查找表。Cloudflare 的 Pingora 是其基于 Rust 的代理框架，承载着全网大量流量，因此任何每次请求的查找开销乘以请求量都会成为严重问题。

## [503 与 504：在 nginx、ALB 和 Cloudflare 中触发机制有何不同](https://dev.to/webpixie/504-vs-503-what-actually-triggers-each-in-nginx-alb-and-cloudflare-45jl) ⭐️ 7.0/10

一篇技术详解指出，503 和 504 错误的根本原因截然不同——503 表示可用性/拒绝问题，而 504 表示延迟/超时问题——并且它们在 nginx、AWS ALB 和 Cloudflare 中的具体触发条件各不相同，需要采取相反的应急措施。 在事故中将 503 误判为 504（或反之）会导致 DevOps/SRE 团队在故障期间采取错误的修复措施，浪费时间并延长故障时间；本文帮助工程师快速判断面对的是上游不可用问题还是后端性能问题。 nginx 的 \`proxy\_read\_timeout\` 衡量的是两次连续读取之间的间隔，而非整个响应的总时长——因此调高该值只是掩盖问题；ALB 的 503 表示目标组中没有健康实例，而 504 表示健康实例在 60 秒空闲超时内未响应；Cloudflare 在源站约 100 秒内无响应时返回的是 524（而非 504），而 Cloudflare 自身的 503 通常意味着边缘节点侧的拦截，而非源站故障。
