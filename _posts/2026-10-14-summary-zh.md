## [ICRAKI 试验：急性肾损伤中间歇性与连续性肾脏替代治疗的比较](https://www.nejm.org/doi/full/10.1056/NEJMoa2608397?ai=nejm&amp;af=R&amp;rss=currentIssue) ⭐️ 9.0/10

《新英格兰医学杂志》发表了 ICRAKI 试验，这是一项多中心、开放标签、非劣效性的随机对照试验，比较了间歇性血液透析（IHD）与连续性肾脏替代治疗（CRRT）在急性肾损伤危重患者中的疗效，旨在确定一种治疗模式是否对患者预后非劣效于另一种。 在危重肾脏病学领域，IHD 与 CRRT 之间的选择已争论数十年，此前超过 15 年的试验未能明确优劣。ICRAKI 试验提供了现代高级别证据，可直接指导全球 ICU 的临床方案和实践指南。

rss · NEJM · 最新文章 · 10月14日 01:00

**背景**: 急性肾损伤（AKI）是危重 ICU 患者的常见并发症，肾脏功能衰竭时常需肾脏替代治疗（RRT）来清除代谢废物并维持体液平衡。两种主要的 RRT 模式是间歇性血液透析（IHD，通常每隔一天进行数小时）和连续性肾脏替代治疗（CRRT，以较慢速率持续 24 小时运行）。此外还存在一种称为持续低效每日透析（SLEDD）的混合模式。CRRT 通常被认为血流动力学更稳定，但需要更多护理和资源；IHD 操作更简便，但可能导致液体和电解质的快速波动。尽管此前已有多项随机试验，尚无确凿证据证明某一种模式优于另一种，因此选择主要取决于临床医生的偏好和机构资源。

## [Anthropic 用自研源码控制系统 Scion 取代 Git](https://simonwillison.net/2026/Oct/13/redesigning-source-control-at-anthropic/) ⭐️ 8.0/10

Anthropic 详细介绍了为何以及如何将源码控制从 Git 迁移到名为 Scion 的自研系统，因为每日合并量从 2026 年 5 月的约 2,500 次增长到 9 月份的超过 30,000 次。该系统由七名工程师组成的团队构建，迁移工作在五个月内完成。 这个案例展示了 AI 驱动的代码生成量正如何颠覆传统的开发工具：Anthropic 的人类工程师已不再是瓶颈——AI 智能体才是，而它们需要的源码控制是为始终在线、高吞吐量的智能体规模工作流设计的，而不是为偶尔联网的人类开发者服务的。 仅主分支历史就近 100 GB，压缩后的工作副本超过 25 GB；Anthropic 每天仅 CI 就要执行约 2,500 万次代码检出，若以原生方式获取将产生超过 600 PB 的 Git 流量。Scion 是中心化的（理念上更像 Subversion 而非 Git），不支持离线（理由是 Claude 是其最重的用户且始终在线），并与一套名为 &quot;Antique&quot; 的新代码审查系统并行运行。

rss · Simon Willison \(AI 跨行业洞察\) · 10月13日 23:00

**背景**: Git 是软件开发领域主流的分布式版本控制系统，其设计前提是单个开发者可以克隆完整历史、离线工作、之后再推送提交。monorepo（单一代码仓库）是指一个仓库包含多个项目，这种做法在 Google、Meta 和 Airbnb 等大公司中很常见。随着 AI 编程智能体能够生成和审查极大数量的代码变更，针对人类规模、离线优先工作流优化的工具可能成为性能瓶颈。Anthropic 的 Scion 是首批明确围绕&quot;智能体规模&quot;假设重新构建的主要生产系统之一。

## [LLM 聊天界面使癫痫脑电图误报减少 80%](https://www.nature.com/articles/s41591-026-04680-4) ⭐️ 8.0/10

**背景**: Oracle 的表存储在由数据库块组成的段中。随着数据插入，新块会被格式化并填充，高水位线随之推进，标记出曾经持有数据的最高块。全表扫描没有索引可循，因此必须从段起始处一直读取到高水位线，逐块检查其中的有效行。由于 DELETE 只是将块中的行标记为已删除，并不会把块归还到高水位线之上的空闲空间，因此扫描代价与表的历史最大规模挂钩，而非当前行数。基于成本的优化器（CBO）会进一步通过块数量的统计信息来估算全表扫描代价，从而放大这种效应。

## [docker system df 为什么会低估磁盘占用，prune 为什么清理不了](https://dev.to/taventix/why-docker-system-df-doesnt-explain-your-full-disk-and-why-prune-frees-less-than-it-says-27gc) ⭐️ 6.0/10

一篇由 AI 生成、可复现的指南详细解释了 \`docker system df\` 不显示的四类隐藏 Docker 磁盘占用来源——主要是容器 JSON 日志，此外还包括 overlay2 层开销、悬空镜像层，以及 Docker Engine 29+ 上的 containerd 镜像存储。文章给出了实测命令，例如对 \`/var/lib/docker/containers/\*/\*-json.log\` 使用 \`du\` 来验证差距。 许多运维工程师在执行 \`docker system prune\` 并看到「0B 可回收」后，仍然遇到「磁盘已满」的告警，因为日志和其他未被统计的内容在持续占用磁盘。弄清这些隐藏字节的来源有助于避免生产环境宕机、简化容量规划，并减少在生产主机上盲目尝试破坏性清理操作。 默认的 \`json-file\` 日志驱动在未配置前没有 \`max-size\` 上限，而 \`docker system df\` 的四行统计（Images、Containers、Local Volumes、Build Cache）刻意不包含日志；文章展示了一个容器产生了 535 MiB 的日志，而其可写层只有 24 KiB。删除正在运行的容器对应的日志文件并不会释放空间，直到 Docker 守护进程关闭该文件，因此 \`lsof +L1\` 能发现 \`du\` 看不到的「幽灵」占用。

rss · Dev.to · 10月14日 19:47

**背景**: \`docker system df\` 统计的是 Docker 管理的对象——镜像、容器、本地卷和构建缓存——但 Docker 的实际数据都存储在 \`/var/lib/docker\` 下，其中 overlay2 文件系统驱动保存了镜像层、容器的可写层以及默认的 \`json-file\` 容器日志。\`json-file\` 驱动会把容器的 stdout/stderr 追加到每个容器对应的文件中（如 \`\*-json.log\`），除非在 \`/etc/docker/daemon.json\` 中通过 \`log-opts\` 设置上限，否则没有大小限制，因此一个输出量大的容器可能在不知不觉中耗尽磁盘。从 Docker Engine 29.0 开始，新安装默认使用 containerd 镜像存储而非 overlay2，这改变了层的统计与清理方式。\`docker system prune\` 只会回收它所追踪的对象——它既不会截断或轮转正在运行容器的日志，也会默认跳过命名卷，除非加上 \`--volumes\` 参数。
